# 打分细则（六维 v1.2）

六维各打 1 到 5 分，加权求总分。每一维都要写一句证据，证据来自实际 API 字段、目录体积、依赖清单、README 正文或检索结果。

报告的权重控制台允许用户拖动滑块改口径并即时重排，所以你给的分数是**初值**而不是定论。把依据写扎实比把数字调好看重要得多，用户会自己试别的权重。

| 维度 | 字段名 | 权重 |
|---|---|---|
| AI 核心技术占比 | `ai_core` | 35% |
| 新颖性 | `novelty` | 10% |
| 时效性 | `timeliness` | 15% |
| 上手难度（越易越高） | `onboarding` | 15% |
| Star 与社区认可 | `stars` | 10% |
| 业务真实性 | `business` | 15% |

## AI 核心技术占比（35%）

核心指模型调用与编排、Agent 决策与状态、检索与排序、embedding 与 rerank、训练微调、评测对齐、上下文与记忆工程。非核心指 CRUD、鉴权、后台 UI、订单支付、部署脚本、文档站。

脚本给两个独立信号，不要只用其中一个。

**路径体积占比**。`probe.ai_share.ai_share`，用 git trees 递归拿全量文件体积，按路径关键词归类。分母已排除文档、测试、示例、benchmark、i18n 语言包、vendored 依赖和压缩产物。

**依赖清单信号**。`ai_dependencies.ai_dep_band`，读 requirements/pyproject/package.json/go.mod/Cargo.toml 里的 AI 库数量。6 个以上=5，3 到 5=4，1 到 2=3，0 个=1。这个信号不依赖目录命名。

| 分 | 路径占比锚点 |
|---|---|
| 5 | 超过 60%，且有自研实现不是纯调库 |
| 4 | 40% 到 60% |
| 3 | 20% 到 40% |
| 2 | 5% 到 20%，AI 是个挂件 |
| 1 | 低于 5%，本质是业务系统 |

**两个信号差 2 档以上时脚本会标 `ai_band_divergence`，这时路径占比不可信，必须人工定分，不要取平均糊过去。** 定分依据写清楚：依赖清单里有哪些 AI 库、核心目录是哪几个、README 架构章节怎么说。

路径占比会被三件事带偏，都要看 `top_other_paths` 和 `top_ai_paths` 自查：

- **命名偏差**。核心代码放在以产品命名的目录里（`serviette/`、`ragflow/`），路径没有 AI 词就被归到 other，占比被系统性低估。脚本的 `naming_bias_warning` 会提示。
- **反向命名偏差**。顶层目录名里带 agent（`tradingagents/`），下面每个文件都命中，占比被高估。
- **vendored 残留**。C/C++ 绑定、第三方源码副本可能没被排除规则覆盖，会撑大分母。

实测校准（2026-11-12 实际跑过）：

| 仓库 | 路径占比 | 依赖档 | 分歧 | 定分与依据 |
|---|---|---|---|---|
| saleor/saleor | 0.1% | 1（无 AI 库） | 无 | 1 分。两信号一致，纯 commerce 后端 |
| pathwaycom/serviette | 9.7% | 5（chromadb/docling/milvus/openai/paddleocr/pgvector/qdrant 等） | 有 | 5 分。核心在 `serviette/indexer/`、`serviette/server/embedder.py`，路径占比低估 |
| infiniflow/ragflow | 30.9% | 5（eino/langgraph/litellm/marker/mistralai/tiktoken） | 有 | 4 分。RAG 核心确实存在，但 Go 侧大量服务与 CLI 代码，且分母含 re2 绑定 |
| TauricResearch/TradingAgents | 85.2% | 4（anthropic/openai/langchain/langgraph/google-genai） | 无 | 5 分。两信号一致，但要扣掉目录命名带来的高估 |
| meilisearch/meilisearch | 11.0% | 3（openai） | 无 | 2 分。搜索引擎本体，AI 是特性不是核心 |

## 新颖性（10%）

看做法和切入角度新不新，不是 star 新不新。

| 分 | 锚点 |
|---|---|
| 5 | 有原创方法且有论文或技术报告支撑，同类实现少于 3 个 |
| 4 | 已知方法的新组合或新场景落地，同类少 |
| 3 | 主流做法的扎实实现，同类 5 到 10 个 |
| 2 | 明显跟随，同类超过 10 个 |
| 1 | 复刻或换皮 |

同类计数靠实际 WebSearch，不靠印象。有 arXiv 链接是加分证据但不是充分条件，很多论文配套代码只是主流做法的实现。

注意 `created_at` 可能是改名前的创建时间。serviette 的 `created_at` 是 2023-07-19，那是它作为 llm-app 仓库的时间，不代表现在这个定位是新的。判断新颖性要看当前做法，不要只看仓库年龄。

## 时效性（15%）

脚本的 `timeliness_score` 已按下面规则算好，可以直接用，但要交叉验证模型代际。

| 分 | 锚点 |
|---|---|
| 5 | 30 天内有推送且近 90 天有 release |
| 4 | 90 天内有推送 |
| 3 | 180 天内 |
| 2 | 365 天内 |
| 1 | 超过 365 天或已归档 |

`releases_90d` 是近 90 天 release 数。有的仓库天天推送但不发版，有的发版频繁但代码没动，两个字段一起看。

再加一层人工判断：README 或 release note 里提到的模型和 SDK 是否属于当前代际。一个 30 天内还在推送但文档只讲两年前模型的项目，时效性要下调并写明。

## 上手难度（15%）

分数越高越容易上手。只看客观的部署与依赖成本。

| 分 | 锚点 |
|---|---|
| 5 | 一条命令或 docker compose 起，自带示例数据，半天跑通 |
| 4 | 一天内，需配 1 到 2 个 key |
| 3 | 两三天，要自己准备数据 |
| 2 | 一周以上，或需 GPU 与多个外部服务 |
| 1 | 装不起来或文档过期 |

判据来自实际文件：`dep_manifests`、`docker_files`、`nested_dep_manifests`、`example_dirs`、`readme_install_hits`。monorepo 的依赖在子目录，`nested-deps` 信号会给出路径，根目录没有依赖文件不等于装不起来。

主语言不计入这一维，见下面「不考核的两件事」。

## Star 与社区认可（10%）

脚本的 `star_score` 已取绝对值档与月增速档的较高者，并且**按平台分别定档**。

GitHub 绝对值档：5 万以上=5，1 万到 5 万=4，3 千到 1 万=3，500 到 3 千=2，500 以下=1。月增速档：2000 以上=5，500 到 2000=4，100 到 500=3，20 到 100=2，20 以下=1。

Gitee 绝对值档：8 千以上=5，2 千到 8 千=4，500 到 2 千=3，100 到 500=2，100 以下=1。月增速档：300 以上=5，80 到 300=4，20 到 80=3，5 到 20=2，5 以下=1。

分平台的理由是量级差一个数量级。实测 hutool 24357、rt-thread 5568、Paddle 4479、CowAgent 665，套 GitHub 阈值会把 Paddle 这种主力框架压到 3 分，把 rt-thread 压到 3 分，而 GitHub 上一个 3 千 star 的普通仓库也是 3 分，这不公平。

**GVP 保底 4 分**。Gitee 最有价值项目是官方人工评选，Paddle、hutool、rt-thread 都是 true，这个信号比裸 star 可靠。

**跨平台镜像要注明**。Gitee 的 `mirrors/` 组织是 GitHub 项目副本，star 只反映镜像热度。还有的项目在 GitHub 很火但 Gitee 侧只有几百 star（CowAgent 就是），这时 star 打低分是对的，但要在证据里写明「Gitee 侧 star 低估了真实影响力，上游 GitHub 同名项目更高」，不要让用户误以为项目冷门。

取较高者是为了不让新项目被老牌框架压死。只看绝对值会让新项目最高拿 1 到 2 分，和新颖性那一维直接对冲，结果偏向中等年龄的中等热门项目。

只给 10% 权重，因为 star 强烈偏向框架和清单，英文项目还占语言优势。`fork_star_ratio` 明显偏高（超过 0.4）要警惕，通常意味着大量人 fork 来交作业。

## 业务真实性（15%）

判据是能不能填完这句话：「____ 在 ____ 场景下遇到 ____ 难题，这个项目用 ____ 解」。填不满就打低分。

| 分 | 锚点 |
|---|---|
| 5 | 有明确用户和真实约束，能看到业务背景、数据来源、规模量级、脏数据与边界情况 |
| 4 | 场景明确难题具体，但业务约束描述较浅 |
| 3 | 场景成立但难题通用，任何领域都能套 |
| 2 | 只有技术场景没有业务场景，能力清单齐全但不知道谁用 |
| 1 | 演示性质，跑个 hello world 或包装一次 API 调用 |

这一维从上一版的 25% 降到 15%，因为 AI 核心技术占比已经承担了一部分筛选。但它同时是 A 档硬准入，见下。

## 档位与准入

- **A 档**：总分 4.0 以上，且业务真实性不低于 3 分
- **B 档**：总分 3.0 到 4.0
- **watch**：总分低于 3.0，或业务真实性 2 分以下
- **读源码档**：`no-run-path` 或 `stale` 命中的进这里，单独列，给阅读路径而不是部署步骤

业务真实性准入是必要的。AI 占比 35% 加新颖性 10% 等于 45%，权重集中在技术含量上，这个组合会系统性地把研究型和 demo 型仓库推上来，而这类恰好业务场景弱。只靠 15% 权重压不住，需要一条硬准入。

AI 占比升到 35% 之后，一个 AI 核心 1 分的仓库最多只能从这一维拿到 0.35 分，业务真实性满分也补不回来。saleor 和 medusa 就是这样掉到 3.0 以下的。这是有意的：这份报告服务的是 AI 方向求职，纯业务系统不该混进主推。

主推控制在 3 到 5 个。如果达标的不足 3 个，就报实际数量，不要降标准凑数。

## 不考核的两件事

**主语言完全不考核**。语言不做门槛也不扣分。Rust、TypeScript、Go 的项目照样能进可跑档。报告里照常列出 `language` 作为事实信息，但不影响分数和档位。上手难度也不含语言迁移成本。

**教程化程度不占权重**。检索到的付费课程、系列实战视频写进候选的风险区，不影响分数和档位。这意味着一个技术含量高但已被大量课程覆盖的项目仍可能进 A 档，风险由用户自己判断。

教程化仍要实际检索，不能省掉这一步，只是结果落在风险区而不是分数里。检索式：仓库名加「教程」「实战」「培训」「课设」。

**写风险时用词要固定**。报告的权重控制台有一个「教程化一票降档」开关，默认关闭，用户打开后教程化重的候选会被踢出 A 档。这个开关读 `tutorial_heavy` 字段；字段缺省时从 `risks` 里按固定词表推断：

- 重档写「教程化严重」或「教程化极重」，推断为 true
- 轻档写「教程化中等」「教程化低」「教程化轻」或「无明显教程」，推断为 false

用了词表外的措辞（比如「教程化程度较高」）推断不出来，开关会静默失效。渲染脚本会拦住这种写法并提示改词，或者你直接在 JSON 里给 `tutorial_heavy` 布尔值绕过推断。

## 产品形态硬门槛

**只要代表某类产品的 Agent 项目，不要库、SDK、框架、引擎、中间件。** 这是淘汰规则不是扣分项，命中直接进淘汰区，不进主表也不进读源码档。

判据是有没有面向最终用户的交互面，不是名字里有没有 agent。脚本的 `product_form` 给四种值：

| 值 | 含义 | 处理 |
|---|---|---|
| `product` | 有终端用户界面，或 CLI 产出人类可读交付物 | 保留 |
| `library` | README 主用法是 import 进代码 | 淘汰 |
| `infra` | 引擎、网关、数据库、中间件这类底座 | 淘汰 |
| `unknown` | 信号不足 | 保留但标注，人工读 README 定 |

判定顺序有讲究，脚本按这个顺序走：

1. **CLI 产出交付物优先**。TradingAgents 同时暴露 Python API 和 CLI，但 CLI 产出研究报告与回测，那是垂直应用。不能因为 README 里有 `from tradingagents import` 就判成库。
2. **库信号压过管理台**。mem0 有 76 个 tsx 文件，但全在 `server/dashboard/` 下，那是给运维看记忆条目的后台。README 主用法是 `from mem0 import`、自称 memory layer 和 SDK，所以是库。**有管理台不等于有产品。**
3. **产品级界面**。`web/`、`frontend/`、`desktop/`、`channel/`、`app/` 这类目录，或管理台之外的前端代码达到 3 个以上。
4. **自称平台且有管理台的判 unknown**。medusa 既有 import 用法又有 admin 包，还自称 commerce platform，这种交人工定，不武断判库。误杀一个真产品比漏掉一个库代价大。

实测校准（2026-11-12 跑过）：

| 仓库 | 判定 | 依据 |
|---|---|---|
| mem0ai/mem0 | library | `from mem0 import`、Library (pip、memory layer、SDK；前端 76 个文件全在 server/dashboard 下，终端用户界面 0 个 |
| meilisearch/meilisearch | infra | 名字含 engine，无终端交互面，AI 是特性不是本体 |
| TauricResearch/TradingAgents | product | CLI 产出单页 HTML 研究报告与回测，交付物优先于 import 用法 |
| pathwaycom/serviette | product | 起服务后 localhost:8989 是聊天界面，前端 index.html 不在管理台路径下 |
| infiniflow/ragflow、HKUDS/DeepTutor、assafelovic/gpt-researcher、khoj-ai/khoj | product | 都有 web 或 frontend 目录 |
| zhayujie/CowAgent | product | channel/ 与 desktop/ 目录，六个 IM 通道加桌面端 |
| medusajs/medusa | unknown | 有 import 用法也有 admin 包，自称 platform，人工定 |

这条门槛也适用于读源码档。读源码要读产品的源码，不是读库的源码。「值得读源码的经典仓库」指的是经典产品，不是经典框架。

## 淘汰模式清单

命中就淘汰，在淘汰区写明原因。

**库、SDK、框架、引擎、中间件**。见上面的产品形态硬门槛。mem0、LangChain、AgentScope、Meilisearch 都属于这类，分数再高也不进候选。

**清单和合集类**。`awesome-xxx`、`xxx-tutorial`、面试题合集、prompt 集合。判据是 `docs-only-structure` 加 `looks-like-list`，或根目录只有 markdown。

**界面复刻类**。各种 UI clone，有界面没业务难题。

**薄包装类**。一个输入框加一次 API 调用的 chatbot、单文件脚本。这类现在还会被 AI 占比和新颖性双重打低。

**脚手架和模板类**。`is_template` 为 true，各种 starter 与 boilerplate。

**归档和停更类**。`archived` 直接淘汰。停更超 365 天进读源码档并标注。

**描述里写着停止维护的**。API 的 `archived` 可能是 false 但描述明写 discontinued，只有读描述才能发现。reactioncommerce/reaction 就是这种。

**无 license 类**。不淘汰，在风险里写明改造后公开托管的法律风险。`custom-license` 和 `no-license` 要分开说，前者是有协议但非标准 SPDX，要读原文。

## 一句话简介与核心技术方格

卡片顶部先给 `summary`，一句话说清这是什么项目，再给 `pitch` 讲立项动机。顺序不能颠倒：读者得先知道这是个什么东西，才有耐心听它为什么值得做。

`summary` 写法：一个 [形态] 的 [做什么] 的 [品类]。比如「一个 pip 装完就能跑的 RAG 服务，文档改了答案跟着变」。不要写成营销语，也不要复述 pitch。

`core_tech` 是核心技术方格，每格一个技术点加一句解释，渲染成分栏网格。给 3 到 5 格。

每一格必须能追溯到实际证据：具体文件路径、依赖库名、README 架构章节或 release note。写「多 Agent 编排」不够，要写清编排在哪、怎么编排。

**AI 核心占比 1 分的仓库要诚实标注。** saleor 和 medusa 这类依赖清单里一个 AI 库都没有的，方格里要有一格明写「AI 核心技术缺失」，其余格子列它真实的工程技术点。不要用业务技术点冒充 AI 核心技术，那会让 35% 权重的那一维失去意义。2 分的仓库仍有真实但次要的 AI 能力，不强制标注缺失，写清 AI 能力边界即可。

方格里的技术点和 `challenges` 可以重叠但视角不同：方格讲「这个项目有什么技术」，难点与解法讲「它为什么需要这个技术，以及怎么解决的」。

## 项目骨架示意图

`skeleton` 用 2 到 5 条泳道把项目主干链路画出来，每条泳道 1 到 3 个方格，格子里是模块名加一句职责，泳道之间用箭头连起来。目的是让用户一眼看懂「这个项目是怎么串起来的」，面试时能顺着链路讲。

**模块名必须是真实路径。** 从 probe 的 `root_dirs` 和 `ai_share.top_ai_paths`、`top_ui_paths` 里取，不要凭印象编目录。`basis` 字段写清依据来自哪些字段，渲染脚本强制要求。

泳道怎么切：按数据流方向切，不按代码目录层级切。典型是「入口 → 编排 → 核心能力 → 出口或存储」。TradingAgents 切成入口、编排、角色 Agent、模型与产出四段；serviette 切成数据源、增量索引、检索与生成、出口四段。

**AI 缺口要画进骨架。** saleor 和 medusa 这类没有 AI 能力的，最后一条泳道直接放一个「无 AI 模块」的格子并说明要自己外挂。这比只给一个 1 分更直观，用户一眼看到缺口在链路的哪个位置。

骨架和 `core_tech` 视角不同：骨架讲「模块怎么连」，核心技术方格讲「每个技术点具体是什么」。同一个模块可以在两处出现，但描述角度要区分开。

## 难点与项目解法

`challenges` 给 3 组，每组一个 `problem` 加一个 `solution`，渲染成左右分栏的难点与项目解法对照。

这是整份报告最有价值的一块。求职者面试时被问的从来不是「你用了什么框架」，而是「你遇到什么问题，怎么解的」。所以难点要写成具体的工程困境，解法要写成项目里真实采用的做法。

**难点的写法**：说清在什么条件下会出什么坏结果，不要写成抽象需求。

好的难点：

> 回测里模型可能读到运行日之后才发布的财报，收益曲线虚高，前视偏差从日期口径漏进来。

差的难点：

> 需要保证回测准确性。

**解法的写法**：给出具体机制加可追溯的来源，版本号、文件路径、依赖库名任选其一。

好的解法：

> 回测只读分析日之前已发布的数据，v0.7.1 专门修了模型日期可能读到运行日之后财报的问题，v0.5.2 起回测只看各分析日已公开信息。

差的解法：

> 使用了 LangChain 框架做数据隔离。

**项目没解决的难点要如实写。** saleor 和 medusa 这类没有 AI 能力的仓库，第三组可以直接写「仓库没有提供解法」并说明要自己实现。这比编一个解法有用得多，用户一眼就知道缺口在哪。

提取来源按优先级：release note 里的重大改动与修复、README 的设计说明与架构章节、`docs/` 设计文档、核心模块命名与注释、issue 区的技术争议。

release note 是最高价值的来源。TradingAgents 的 News 段落逐版记录了回测口径变更和前视偏差修复，一条 release note 往往就是一组现成的难点与解法，比 README 的功能清单有用得多。

如果读不出三组真实的难点与解法，在风险里写明「难点与解法不足」，不要编。

## 时间预算怎么影响判断

两周：只推上手难度 4 分以上的，改造范围收敛到一个模块。

一个月：上手难度 3 分以上都行，可以承接需要自己备数据的。

三个月以上：可以接论文复现和复杂依赖，上手难度权重可下调，把权重挪给新颖性。调权重要在报告的 `meta.weight_note` 里写明调整后的数值和原因。
